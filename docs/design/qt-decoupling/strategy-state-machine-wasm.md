# 状态机策略的落地契约（ADR-D16 草案）

> 状态：草案，未实现。承接 ADR-D15（表达力边界）。
> 用户需求定性：**状态机策略**——逐 bar 在线推进、有状态、转移逻辑过程式。
> 结论：**载体只能是 WASM（L3a）**。DSL 无控制流（ADR-D15 §1），L3b 是离线信号、做不了逐 bar 状态推进。

---

## 1. 为什么只剩 WASM

| 要求 | DSL | L3b 外部信号 | WASM | 内置 Go / `.so` |
|---|---|---|---|---|
| 逐 bar **在线**推进 | ✅ | ❌ 离线批量 | ✅ | ✅ |
| **有状态**且可恢复 | ⚠️ 仅算子内递推 | ⚠️ 状态在你自己进程 | ✅ `get_state`/`set_state` | ✅ |
| 过程式转移逻辑（**图灵完备**） | ❌ | ✅ | ✅ | ✅ |
| 沙箱（AI / 第三方策略） | ✅ 天然 | 进程外 | ✅ | ❌ |
| Windows 可用 | ✅ | ✅ | ✅ | ❌ `.so` |

**WASM 是唯一同时满足前四项且跨平台的载体。**

---

## 2. 三层状态模型（核心设计）

| 层 | 位置 | 读写频率 | 作用 |
|---|---|---|---|
| **工作副本** | wasm 线性内存 | **每 bar** | 状态机的热状态（当前态、计数器、冷却期） |
| **宿主状态** | `BarContext.State`（`get_state`/`set_state`） | **按日期边界** | 持久化真相；实例可驱逐/重建的依靠 |
| **落库** | `quant.strategy_state`（`StateStore`） | 按日期边界 | 断点续跑 |

**关键裁决：不要每 bar 都 `set_state`。** 每 bar 跨 host 边界写状态会把调用次数翻倍、且让"状态真相"在两处抖动。做法是：**wasm 内存里跑热状态，到日期边界 flush 一次**。

这个做法与 `pkg/strategy/checkpoint.go` 已有的裁决天然一致——该文件明写（原文要点）：

- 保存点**必须对齐日期边界**；
- 原因：多 symbol 平铺流（`[d1sA, d1sB, ...]`）下若在同一日期块中间保存，续跑按 `Date <= ts` 跳过会**静默丢 bar**（d1sB 永远不跑）；
- 异常退出时"尽力保存"，但**不在日期边界绝不保存**。

⇒ **WASM 状态机直接复用这套语义**，不要另发明一套。

---

## 3. 恢复语义：检查点 + 重放

从落库恢复时，wasm 内存里的**中间状态已经丢失**，因此：

1. host 载入最近检查点（对齐日期边界）的 `BarContext.State`；
2. 重建实例 → `initialize` → **`load_state`**；
3. **重放该日期块剩余的 bar**（从检查点之后的一根开始）；
4. 继续正常推进。

验收判据沿用 ADR-028 §7 的三路一致性：**Batch ≡ Step 从零 ≡ Step 从持久化恢复**。这条已有要求正好是状态机的天然验收。

## 4. 必须补的协议缺口（实测发现）

| # | 缺口 | 证据 | 处置 |
|---|---|---|---|
| 1 | **状态写入用固定偏移 4096，且无长度上限** | `hostGetState` 里 `m.Memory().Write(4096, val)`，越界才 panic；params 写在 offset 0 | 改为协商偏移或专用状态区；**host 侧强制单 key / 总状态 / key 数上限**（否则策略能把状态当磁盘） |
| 2 | **没有 `reset` / 切换 symbol 的操作** | 全包 grep `reset\|set_symbol\|SwitchSymbol` 零命中 | ~~per-symbol 状态机目前只能「每 symbol 一个会话」~~ **（2026-10-19 裁决 D25：定为混合模型——`scope=market` 单实例横截面；`scope=symbol` 分片实例、每实例 symbol 固定，故不需要 reset。此缺口对 symbol scope 关闭）** |
| 3 | **状态没有 schema 版本** | `BarContext.State` 是裸 `map[string][]byte` | 状态内嵌 `schema_version`；版本不匹配 ⇒ **fail-closed 拒绝恢复**，绝不静默按旧格式解释 |
| 4 | **状态序列化可能不确定** | 若用 map/JSON 无序编码 | 固定顺序编码（与"喂 bar 按 symbol 字典序"同类问题），否则 K15 双跑对拍会假失败 |

---

## 5. 确定性红线（状态机最容易踩的四条）

1. **状态转移不得依赖 wasm 内部时钟或随机**——env-only 白名单已经挡住（无 `clock_time_get`、无 `random_get`）。若状态机确实需要随机，走 ADR-D15 §4 的四条补丁（host 提供 seed 化 PRNG + 状态持久化 + 禁 WASI + seed 留痕）。
2. **host 必须保证 `T` 单调、每 bar 只推进一次**——否则状态机会被重复触发，且不可复现。
3. **状态序列化必须确定**（见 §4.4）。
4. **落盘时机归 host，不归策略**——不允许策略通过 host 函数主动要求"现在落盘"，否则会破坏日期边界对齐。

## 6. PoC 修订（针对状态机，替换原 P3/P4 的部分内容）

| # | 任务 | 通过判据 |
|---|---|---|
| P1 | 装 TinyGo，编出 **env-only** 的状态机 wasm（含 if/循环/状态表） | `ValidateImports` 通过 |
| P2 | 实现**真实状态机策略**：如"持仓状态机 + 冷却期 + 分层加仓"（不是 toy 均线） | 能跑通 initialize → on_bar × N → finalize |
| P3 | **三路一致性**：Batch / Step 从零 / Step 从断点恢复，结果逐位一致 | 复用 `checkpoint.go` 的日期边界语义 |
| P4 | **性能基准（按 v2 两种 scope）**：`scope=market` 的 727 次 on_bar 开销；`scope=symbol` 的 363 万次外推 | 给出 ms/bar 与总耗时；确认 market scope 为默认形态 |
| P5 | 与内置 Go 同逻辑策略 dualrun 对拍 | K15 级别一致 |

## 7. 分期（在 ADR-D14 基础上的调整）

| 阶段 | 内容 |
|---|---|
| **S1a** | 补协议缺口 §4（状态偏移/上限、schema 版本、确定性序列化） |
| **S1b** | 装工具链 + 状态机 PoC（P1-P5） |
| **S2** | 编译服务 + artifact 登记 + `carrier=wasm` 接线到 `SignalProvider` |
| **S3** | 内置策略登记、统一入口 |

**DSL 与 L3b 都不再阻塞状态机路线**：状态机直接走 S1 起。

---

## 8. 一句话结论

**状态机 ⇒ WASM；状态三层（wasm 热副本 / host 真相 / PG 落库）；落盘对齐日期边界（复用 `checkpoint.go` 既有裁决）；恢复 = 载入检查点 + 重放；四个协议缺口必须在 PoC 前补齐。**
