# 服务拆分方案：数据 / 风控 / 策略 + 候选清单（ADR-D18 草案）

> 状态：草案，未实现。工程周期：② 架构设计。
> 起因：用户提出 ① 拆数据服务、回测/实盘无状态（数据与策略从外部供给）② 摘风控为 external risk control（支持实盘）③ 策略服务 ④ 还有什么可摘。
> 📌 **我的假设**（如与实际不符请纠正）：团队 = 你 + AI agent（1-2 人）；阶段 = P2 演进中；部署 = 单机本地栈，无多机诉求；预算有限、无强合规。

---

> **与 ADR-027 的对账注（2026-10-19 审查补）**：ADR-027（Proposed）已给出服务拆分终态口径 **5（compose 容器 7）**（含 data A/B 二分、策略服务、reduction-service 等）。本 X 线列出的六个候选是**按能力边界**的提取清单（数据/策略/风控/分析/编排/网关），**不是**最终服务拓扑——两者未逐一对账。升格裁决时以 ADR-027 §2 的拓扑为基准做合并/拆分对账（例如分析服务可能并入既有服务、网关可能不单列），X 线只负责"边界收口成 port"这一层。

## 1. 摘不摘的判据（先定规矩，再看候选）

参考库《架构模式》§七/§八：**数据归属唯一、依赖单向、按业务能力划分；先拆数据边界，再拆服务**。据此定 5 条：

| # | 判据 | 为什么 |
|---|---|---|
| 1 | **数据归属唯一**：该模块有自己独立的表/真相源 | 共享数据库的"伪服务"= 分布式单体 |
| 2 | **变更节奏不同**：可以独立发布 | 否则拆了还得一起发 |
| 3 | **扩容诉求不同**：算力/可用性要求不一样 | 拆的意义 |
| 4 | **边界稳定**：接口不会频繁变 | 频繁变的接口拆出去 = 运维负担 |
| 5 | **不在内循环热路径上**（不需要逐 bar/逐笔同步调用） | **最关键的一条**，见 §2 |

**第 5 条是硬闸门**：任何"每 bar / 每笔"的同步远程调用，都会把 ns 级变成 ms 级（10³~10⁶ 倍），并毁掉确定性与可复现。这条不满足，前 4 条再漂亮也不摘。

## 2. 统一模式（三个服务共用同一套架构）

**真相源外置 + 内容寻址副本 + 运行期本地执行 + 内循环零网络。**

```
[策略服务]  定义/源码/版本/artifact      ──┐
[数据服务]  行情/因子/基本面/快照 hash   ──┼──→  run 前拉取（1 次）→ 内容寻址缓存
[风控服务]  规则/限额/熔断配置          ──┘        ↓
                                          [回测/实盘内核] 内循环逐 bar · 零网络
                                                   ↓ run 结束
                                          结果记录 {策略 hash, 数据快照 hash, 风控规则 hash}
```

这个模式你们已经用过两次（策略 artifact、因子 `version_hash`），**第三次直接套用，不要发明新机制**。

收益：可复现（三个 hash 记录在结果里）· 离线可用（缓存命中即可跑）· 服务挂了不影响已在跑的 run。

## 3. 「回测无状态」的精确含义（必须先说清，否则会走歪）

| 含义 | 判定 |
|---|---|
| ① 进程无持久化状态（不拥有数据库、不写业务表），每次 run 从零加载 | ✅ **这就是目标** |
| ② 进程可有**内存/本地缓存副本**，run 期间零网络 | ✅ **推荐形态** |
| ③ 逐 bar 远程取数（真·无状态） | ❌ **禁用**：内循环网络化 + 前视不可控 + 可复现性丧失 |

⇒ 准确说法：**内核是有状态的计算过程，但无持久化状态**。数据集与策略在 run 开始时一次性加载（按 `RunSpec` 的 universe × 日期窗口 × 频率），run 期间本地执行，run 结束释放。

**数据集也要内容寻址**：`dataset_snapshot_hash`（票池 + 日期窗口 + 频率 + 数据版本的 sha256）记入回测结果——这样"同一份数据跑出的结果"才可复现，与 `strategy_ref` 的 hash 是同一套逻辑。

## 4. 三个服务的边界设计

### 4.1 数据服务（✅ 摘，判据全过）

| 项 | 内容 |
|---|---|
| **管什么** | 行情（`marketdata` D1 规范层）· 因子定义/计算/治理（`pkg/data` 的 Computer、D3 定义库、D4 登记）· 基本面/宏观/板块/产业链 · 数据源适配与 ETL（`pkg/data/source` 8 适配器）· 同步调度（`pkg/sync`） |
| **不管什么** | 不算信号、不下单、不做回测撮合 |
| **数据归属** | `quant.*` schema 归它（行情、因子定义、基本面）；**引擎不拥有任何业务表** |
| **对外接口** | `GET /datasets/resolve`（按 universe+窗口+频率 → 数据集元数据 + hash）· `GET /datasets/{hash}`（拉数据）· `GET /factors/{name}@{hash}`（因子定义与值） |
| **引擎侧** | 数据集按 hash 缓存；run 前拉 1 次；内循环零网络 |
| **注意** | `marketdata.Router` 是 D1 规范层的唯一入口（已有），拆出后它就是数据服务的**内部实现**；引擎只认接口 |

### 4.2 风控服务（⚠️ 摘，但必须**两层**，不能整体搬）

你的诉求是"external risk control + 支持实盘"。**直接把裁决搬出去不可行**（第 5 条硬闸门），正确形态是拆成两层：

| 层 | 位置 | 职责 | 频率 |
|---|---|---|---|
| **规则真相源 + 聚合监控**（外部服务） | 风控服务 | 规则/限额/熔断配置的**定义、版本、审批、审计**；跨策略/跨账户聚合风险；实时监控与告警；**下发熔断指令**（如"禁止开仓"） | 异步 / 准实时 |
| **同步裁决**（进程内） | `RiskPolicy` 对象 | per-order / per-bar 硬约束：仓位上限、止损止盈、regime、VaR、手数、涨跌停、T+1 | **逐 bar / 逐笔，零网络** |

**支持实盘怎么落**：
- 实盘订单路径调用**同一个 `RiskPolicy` 对象**（与回测同口径）——这正是"回测可信"的前提，也是 dualrun K15 能对齐的原因；
- 风控服务提供：规则真相源 + 全账户聚合 + **熔断开关下发**（实盘进程轮询/订阅，不是逐笔同步调用）；
- **fail-closed 语义**：规则拉取失败 ⇒ 拒绝启动或用已缓存规则并告警；熔断开关未收到 ⇒ 按默认规则执行（本地缓存）。

⚠️ 现状提醒：`pkg/risk` 已被回测与实盘共用（`live/interfaces.go:34 OrderIntent = risk.OrderIntent`、`risk.CheckOrder`），**这层本来就是共享能力**，拆分时它就是"进程内裁决"的天然载体；而 `compliance`（合规报送）+ `alert`（六类检测器 + 通道）**正好是聚合监控层的现成零件**，建议并入风控服务。

### 4.3 策略服务（✅ 摘，已设计完）

见 `strategy-source-of-truth-and-cache.md` / `strategy-asset-service-api.md`：定义/源码/版本/artifact 真相源，引擎缓存副本，`strategy_ref{id@hash}`，五道校验门。**只管定义，不算信号。**

## 5. 还能摘什么：候选清单（按判据打分）

| 候选 | 数据归属 | 独立发布 | 扩容诉求 | 边界稳定 | 非热路径 | **建议** |
|---|---|---|---|---|---|---|
| **数据服务** | ✅✅ | ✅ | ✅（IO 型） | ✅ | ✅（预取） | **摘**（用户已提） |
| **风控服务**（规则 + 聚合监控） | ✅ | ✅ | ✅（监控型） | ✅ | ✅ | **摘，两层形态** |
| **策略服务** | ✅✅ | ✅✅（策略迭代最快） | ✗ | ✅ | ✅ | **摘**（已设计） |
| **分析/报表服务** | ✅ | ✅✅（报表需求最易变） | ✅（计算型） | ✅ | ✅（回测后处理） | **摘，性价比最高** |
| **回测编排/worker 服务**（job/batch/walkforward） | ✅ | ✅ | ✅✅（算力可横向扩） | ✅ | ✅ | **摘**，但依赖内核能力 |
| **券商/数据源接入网关**（`live/broker` + `pkg/data/source`） | ✅ | ✅✅（外部 API 易变） | ✅ | ✅ | ✅ | 摘（实盘链路有延迟诉求，需谨慎） |
| 合规与告警（compliance + alert） | ✅ | ✅ | ✅ | ✅ | ✅ | **并入风控服务**，不单列 |
| 回测内核（contracts/execution/tracker/metrics/auction/state） | — | — | — | — | ❌ **热路径** | **不摘**（核心语义，进程内） |
| domain / expression / indicator | 是库不是服务 | — | — | — | — | **不摘**（公共库） |
| storage 连接能力 / kit 工具 | 共享基建 | — | — | — | — | **不摘** |

### 5.1 值得重点说的两个新候选

**① 分析/报表服务 —— 性价比最高**
- 它正好是你们已登记的缺口 **BE-05/BE-06**（基准对比、业绩归因、参数敏感性、蒙特卡洛，回测族内零实现）；
- 性质是**纯函数 + 只读数据**：输入 = 回测结果 + 基准 + 因子值，输出 = 报表；天然无状态、天然可独立扩容、天然不碰内循环；
- 拆出来的另一个好处：**报表需求变了不用动引擎**（这是"廉价拓展"目标的最直接兑现）。

**② 回测编排/worker 服务 —— 算力的正确出口**
- `job` / `batch` / `walkforward` 本来就是应用编排而非引擎（BE-03 已登记）；
- 你提到"批量扫描算力可能打满"——**正确出口就是这个**，而不是把内核拆成服务；
- 形态：任务队列 + worker 池，每个 worker 调用内核能力（进程内或按 hash 加载 artifact）。

### 5.2 摘出去的顺序建议（按"数据归属"优先，参考库：先拆数据边界）

```
① 数据服务（数据归属最重，其他都依赖它）
② 策略服务（已设计完，artifact + 缓存模式已定）
③ 风控服务（规则层 + 聚合监控，裁决留进程内）
④ 分析服务（补 BE-05/06 缺口）
⑤ 编排/worker（算力出口）
⑥ 券商/数据源网关（最后，实盘延迟敏感）
```

## 7. 风险

| 风险 | 兜底 |
|---|---|
| **把"无状态"理解成逐 bar 远程取数** | §3 已写死禁令；护栏可加（内循环禁 HTTP 调用） |
| 数据集快照 hash 不一致导致不可复现 | 快照规则先定（票池 + 窗口 + 频率 + 数据版本），与 `strategy_ref` 同款 |
| 风控服务挂了实盘下单 | fail-closed：用本地缓存规则 + 告警；启动时拉取失败则拒绝启动 |
| 1-2 人团队维护 5-6 个服务 | **现在不要真拆进程**：先把边界收口成 port + 服务接口，进程拆分等触发条件（见工程档案 §7 P3） |
| 拆出的服务互相依赖成网 | 依赖方向：应用 → 服务 → 内核 → kit/contracts；服务之间**不横向互调**，要协作走内核或编排层 |
